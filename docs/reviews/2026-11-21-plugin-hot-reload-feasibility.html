01

结论先行

把目标拆成“能力刷新”和“页面状态无损”两条线，可行性结论不同；前者可以进入 MVP，后者需要新增插件契约。

Verdict
CONDITIONAL
GO

建议以“选择性插件重载 + 保留未受影响页面”为 MVP，保留全量重载作为回退路径； 不承诺受影响插件页面内部状态无损，不承诺原生扩展热替换，不承诺插件自建线程的强制回收。

SCOPE: ENABLE / DISABLE / UPDATE / ROLLBACK / REMOVE

可以做到 / 需要条件 / 不要承诺
  • 可以做到 只卸载/加载目标插件及其反向依赖者；未受影响插件的 on_load / on_unload 不被调用。
  • 可以做到 保留未受影响页面实例、滚动位置与表单状态；插件管理原生页不再被销毁。
  • 可以做到 按 owner 清理托盘、快捷键、事件订阅、服务、设置页与模块缓存；这些能力已有现成句柄。
  • 需要条件 受影响页面会被重建；页面内部状态需要插件在 on_surface_leave 写入 ctx.settings / ctx.storage，或新增 surface 状态协议。
  • 需要条件 更新失败自动回滚需要事务化文件替换、旧版本重载与状态恢复；现有 manager 只归档旧版本，没有恢复路径。
  • 不要承诺 原生扩展（.pyd / .so / .dll）热替换、插件自建线程/定时器的强制回收、进程隔离。
为什么现在具备条件 加载器本来就是按插件工作的。 load_plugin() / unload_plugin() 已经按唯一模块名导入、按插件根目录兜底清理 sys.modules， 托盘、快捷键、事件、服务、设置都以 plugin_id 为 owner 清理；页面按 plugin_id/surface_id 派生 objectName 并懒构建。 真正欠缺的不是“能不能卸载一个插件”，而是“窗口层不要顺手把所有页面和所有插件都重建”。
02

现状基线

当前一次启停/更新，实际执行的是“全量卸载 → 全量导入 → 全量页面销毁 → 菜单重建”。

当前重载链路

  1. 插件管理页写入状态并请求重载
    _set_plugin_enabled() 先改 registry.json，再由 schedule_reload() 延迟 120ms 调 reload_plugins(page_object)。 （plugin_store/page.py:962-980、1242-1257）
  2. 窗口销毁所有已构建页面
    _clear_pages() 对页面栈做 removeWidget → hide → setParent(None) → deleteLater，包括插件管理这个原生页。 （gallery/window.py:306-323）
  3. 运行时全量重载
    runtime.reload() → shutdown(clear_registry=False, dispose_tray=False) → unload_all(records) → 清空 records → 重新读取 registry → bootstrap() 重新加载全部插件。 （gallery/runtime.py:233-244）
  4. 菜单与页面重新装配
    left_menu.clear_menus() + add_menus(get_menu_items(...))；再按原生页/原路由/默认路由重新打开页面。 （gallery/window.py:246-263；guicore/window/left_menu/menu.py:94-147）
图 1 · 当前全量路径与建议选择性路径的差异；共享能力层按 owner 清理，不需要整体销毁。 页面实例保留是 MVP 的核心收益

03

可行性矩阵

按用户提出的八个维度拆开判定；结论不是单一“能/不能”，而是分层的“可直接做 / 需新增契约 / 不建议承诺”。

八个维度的可行性判定
维度判定关键依据前置条件
改动范围 中等 / 可控 加载器、注册表、能力句柄已经按插件工作；主要新增窗口层的“选择性失效”和运行时事务编排。 不修改插件 API v2；不引入进程隔离。
插件生命周期 可定义 现有 on_load → surfaces → on_locale_changed → on_surface_enter/leave → on_unload 已覆盖卸载/加载；可增加内部重载状态机。 明确卸载顺序：依赖者先卸，提供者先装。
状态保持 部分可行 未受影响页面可原样保留；受影响页面没有通用状态序列化协议，只能重建。 插件把视图状态写入 settings/storage，或新增可选 surface 状态协议。
兼容性 高 API v2 不变；清单 schema 不变；现有插件无需改代码即可享受“只刷新自己”。 新增错误码与内部接口；文档同步。
稳定性 中等 模块缓存清理已有；但插件线程/定时器、Qt 信号、原生扩展锁定不可强制治理。 插件规范约束 + 重复重载测试 + 失败隔离。
资源释放 中等 托盘/快捷键/事件/服务/设置都有 owner 清理；页面用 deleteLater；模块可清。 释放顺序固定；插件 on_unload 必须幂等并停止自建资源。
异常回滚 中高复杂度 manager 有 staging/history，但 _promote() 在“旧目录已移走、新目录放置失败”时没有恢复动作。 事务化 promote + 旧版本重载 + 状态回写；数据迁移不回滚。
性能影响 高收益 20 插件实测单插件重载 11.65ms，全量 220.54ms；未受影响页面不再重建。 菜单/托盘仍是 O(N) 重建，插件数很大时需再优化。
推荐结论

以“按插件选择性重载”进入 MVP；把“页面状态无损”和“原生扩展热替换”明确排除在第一版承诺之外。 全量重载保留为 force_full=True 的回退路径，任何事务无法收敛时回到已知可用状态。

不推荐的做法

直接在 reload_plugins() 里按 plugin_id 过滤后继续调用 runtime.reload()： 它仍会重建所有页面、重读整个 registry，并把未受影响的插件也卸载重载，等于没有解决问题。

05

插件生命周期

重载不是一个新的插件协议，而是基座内部的“卸载旧实例 → 替换文件/状态 → 加载新实例”事务。

图 2 · 建议的重载状态机；橙色为回滚路径，红色为失败隔离。 内部状态，不进入插件 API

推荐事务顺序

  1. 计算受影响集合
    目标插件 + 所有直接/间接依赖它的插件（反向依赖闭包）。卸载顺序为依赖者优先，加载顺序为提供者优先。
  2. 预检新版本
    读取新清单、校验 API/依赖/Surface impl 存在性；不执行插件代码。预检失败直接返回，旧实例继续运行。
  3. 离开当前 Surface
    如果当前页面属于受影响集合，先调用 on_surface_leave(surface_id)，再销毁该插件页面；其它页面不动。
  4. 卸载依赖者与目标
    on_unload() → clear_shortcuts → clear_tray → clear_events → clear_services → clear_settings → 清模块缓存。
  5. 替换文件（仅更新/回滚）
    旧版本先进入 history；新版本从 staging 放入插件目录；清理插件内 __pycache__；importlib.invalidate_caches()。
  6. 按顺序加载
    提供者先加载，依赖者后加载；每个插件失败时先清理它已注册的部分句柄，再决定整体回滚或隔离。
  7. 刷新派生能力
    强制刷新插件语言命名空间；重建左菜单；重建托盘菜单；通知设置页命名空间；保留当前路由或回退。
  8. 记录结果
    写 plugin.reload 遥测：原因、目标、受影响数量、页面销毁/构建数、耗时、是否回滚。
现有代码的一个关键缺口 运行时加载顺序没有按依赖拓扑排序。 bootstrap() 按 _run_roots() 返回顺序加载（开发目录优先，然后 registry 记录顺序），并没有使用 resolver 的拓扑结果。 如果依赖者在 on_load 中解析 ctx.services，提供者可能尚未加载。选择性重载必须显式按拓扑顺序卸载/加载，否则会把已有的隐性顺序问题放大。
06

状态保持

“避免页面整体重建”可以做到；“所有状态都不丢”不能。需要把状态分成基座状态、未受影响页面、受影响页面三层来承诺。

不同对象在选择性重载下的状态保持能力
对象当前全量重载选择性重载目标实现方式 / 边界
插件管理原生页 被销毁，重建后靠 stash 恢复模式/搜索/选中/滚动 完全保留 不再调用 _clear_pages()；页面实例、滚动、输入焦点都不变。
未受影响插件页面 被销毁并重建，内部状态丢失 完全保留 只移除目标插件对应的 page_<route>；其它页面不 setParent(None)。
受影响插件页面 销毁并重建 重建，状态尽力保留 没有通用 QWidget 状态序列化；插件应在 on_surface_leave 把草稿写入 settings/storage，在新页面构建时恢复。
设置窗口中的插件页 设置窗口通常不参与重载；插件页可能指向旧注册表 可原地刷新 settings_page_bus().notify(plugin.<id>)；现有 _rebuild_plugin_page() 保留草稿与滚动。
插件数据 / 设置 / 存储 磁盘保留，unload 不删除 保留 data_dir、settings/plugins/<id>.yaml、ctx.storage 的语义不变；删除插件才 purge。
托盘 / 快捷键 全量清理后重建 按 owner 刷新 目标插件条目移除并重新注册；其它插件条目保留。用户看到的顺序/形态由基座重新裁决。
当前路由 / 标题 重载后按原路由/默认路由重建 保持不变或安全回退 当前页面不受影响则不动；受影响则在新插件加载后重新打开同路由；路由消失则回退默认/原生页。
窗口几何 / 主题 / 语言 通常不受影响 不动 选择性重载不触碰窗口状态；语言命名空间单独刷新。
已确认的语言刷新缺口

Language.apply() 的早退签名只包含基座语言内容；插件语言表变化时，即使调用 refresh_language_namespace()，Language.app 也不会重新注入。 本地验证：把插件语言从 1 改成 2 后再次刷新，读到的仍是 1。

影响：更新插件后，菜单标题/插件内文案可能保持旧值，直到用户切换一次语言。

已确认的日志前缀缺口

GalleryContextImpl 用 sllkgui.plugin.<id> 复用同一个 logger，并靠 _sllkgui_bridged 防止重复挂 handler。插件从 v1 更新到 v2 后，旧 handler 的 [plugin:id@v1] 前缀仍然存在，新上下文不会替换它。

影响：热重载后的日志版本号可能错误，排障时容易误判当前运行版本。

R-02 旧插件线程/定时器未停止，回调命中已销毁控件 中 高 on_unload 未停 QTimer/QThread，或信号仍连接旧对象 把“停止自建资源”写入插件规范；重复重载测试；失败隔离；开发模式泄漏检测。
R-03 依赖者缓存旧服务实例，提供者更新后状态不一致 中 中高 依赖者在 on_load 取到旧 ctx.services.get() 结果 重载反向依赖闭包；提供者先加载、依赖者后加载；服务解析失败时显式报错。
R-04 更新流程先替换文件、后卸载旧插件，旧代码读到半新文件 中 高 PluginManager.update() 在后台线程完成 _promote()，之后才由 UI 触发重载 事务化：先停旧实例，再 promote；或 staging 完成后由主线程统一提交。
R-05 插件语言表变化不生效，菜单/页面文案陈旧 高 中 Language.apply() 按基座语言签名早退（已实测复现） 增加强制刷新入口：重置签名或直接重注入 Language.app；重载后调用。
R-06 日志前缀仍显示旧版本 高 低 _sllkgui_bridged 阻止新 handler，旧 handler 的 prefix 不变 卸载时移除 handler，或让新上下文更新 prefix；加断言测试。
R-07 旧页面未从对象树移除，findChild 命中旧页面 中 中 ensure_registered_page() 幂等返回已存在控件 只移除目标插件页面，并先 setParent(None) 再 deleteLater；断言页面身份变化。
R-08 更新失败后 registry 仍指向新版本，启动时反复失败 中 中高 manager 先写状态，load 失败只记录 error 加载成功后再提交状态；失败回滚 InstalledPlugin 与目录；启动时跳过坏插件并提示。
R-09 依赖顺序未拓扑化，提供者尚未加载 中 中高 bootstrap() 按 roots 顺序加载，未按 dependencies 排序 选择性重载显式拓扑排序；顺带修正启动加载顺序；加服务解析测试。
R-10 菜单全量重建导致闪烁或当前按钮丢失 中 低 left_menu.clear_menus() + add_menus() 重建后按 route 恢复 active；插件多时再做增量 remove/add。
R-11 重载期间并发触发托盘/快捷键/页面构建，状态撕裂 中 中 托盘回调、快捷键、导航都可能在主线程事件循环中进入 运行时单飞锁；重载期间禁用目标动作；重复请求返回 PLUGIN_RELOAD_IN_PROGRESS。
R-12 _promote() 失败时旧目录已在 history、目标目录缺失 低 高 旧目录移走后 place_staging() 抛错 事务化 promote：失败立即把 history 目录移回；状态不变；记录 PLUGIN_RELOAD_FAILED。

资源释放

选择性重载的频率远高于全量重载，资源释放必须“可验证”，不能只依赖插件自觉。

资源释放清单
资源现有清理入口选择性重载中的动作验证方式

异常回滚

回滚分为“文件回滚”“运行时回滚”“状态回滚”“数据回滚”四层；基座只应承诺前三层。

失败点与回滚动作
失败点已发生的副作用回滚动作用户可见结果
预检失败（清单/依赖/impl） 无；旧实例仍在运行 不卸载、不动文件；记录错误 提示错误码；旧页面继续可用
on_unload 抛错 部分能力可能已清理 继续清理剩余句柄；记录 warning；目标标记为不可用 插件被卸载；若无法恢复，提示“需重启/重新启用”
文件 promote 失败 旧目录可能已在 history，目标目录缺失 把 history 目录移回 plugins/<id>；恢复原 InstalledPlugin 旧版本继续运行；错误提示；registry 不变
新版本 on_load / import 失败 旧实例已卸载；新文件已就位 清理新实例半注册句柄；新目录移入 trash/history；旧目录移回；重新加载旧版本 旧版本恢复运行；错误提示；版本号回退
新版本加载成功、依赖者加载失败 提供者已升级；依赖者不可用 隔离失败依赖者并禁用；提供者保留新版本；提示用户可回滚提供者 主插件可用；依赖功能暂时不可用
Surface 构建失败 插件已加载，页面未生成 不回滚插件；移除失败页面；提示错误码 插件其它 Surface 可用；当前页显示错误提示/空状态
旧版本重载也失败 旧代码/旧文件不可用 禁用插件；保留目录与错误详情；启动时跳过 插件不可用；用户可重装/回滚/查看日志
数据迁移失败 插件数据可能已被新版本改写 不自动回滚数据；插件负责 schema 版本与备份 提示插件数据迁移失败；建议从备份恢复

事务模型

两阶段提交
  1. Prepare
    下载/校验到 staging；读取新清单；验证依赖与 Surface impl；不执行插件代码。
  2. Quiesce
    离开当前 Surface；卸载依赖者与目标；清理句柄与模块。
  3. Commit
    promote 文件；加载新插件；刷新语言/菜单/托盘/设置。
  4. Compensate
    任一步失败：按相反顺序恢复文件、重新加载旧版本、恢复 registry 状态。
必须先修的现有缺口

_promote() 先 move_to_history() 再 place_staging()； 如果放置失败，没有把旧目录移回的分支。当前调用方只能看到异常，registry 仍可能指向新版本。

建议在 GalleryStore 或 PluginManager 增加 promote_transaction()：返回 undo 闭包，失败时执行；并把“状态写入 registry.json”延后到加载成功之后。

数据回滚边界 插件数据、用户设置、缓存不属于基座事务。 基座保留目录、不删除数据；更新失败时不会把数据回滚到旧 schema。插件必须在自己的数据中维护 schema_version、迁移失败可回退的备份；否则“运行时回滚成功”仍可能留下不可用的数据。

目标值（建议，不是当前实测）

  • 主线程单次同步段不超过 100ms；超过时给出忙碌提示或拆分步骤。
11

推荐实施边界

把“必须做”“可以晚点做”“明确不做”分开，避免第一版把回滚、状态协议和开发热重载全部混在一起。

MVP 范围
  • 单插件启用/停用/更新/回滚/卸载的选择性重载。
  • 反向依赖闭包：提供者更新时自动重载依赖者。
  • 只销毁目标插件页面；未受影响页面与插件管理页保留。
  • 左菜单重建后恢复当前路由/按钮；路由消失时安全回退。
  • 托盘/快捷键/事件/服务/设置按 owner 清理与重注册。
  • 更新失败的文件回滚 + 旧版本重载（尽力而为）。
  • 单飞锁与 PLUGIN_RELOAD_IN_PROGRESS。
  • 全量重载回退开关 force_full=True。
  • 原生扩展检测 → RESTART_REQUIRED。
MVP 明确不承诺
  • 受影响插件页面的内部状态无损。
  • 插件自建线程/定时器的强制回收。
  • 原生扩展热替换。
  • 插件数据 schema 的自动回滚。
  • 进程隔离/沙箱。
  • 开发目录文件监听（放到二阶段）。

建议的接口形状

class GalleryRuntime:
    def reload_plugin(self, plugin_id: str, *, reason: str = "manual") -> ReloadResult: ...
    def reload_plugins(self, plugin_ids: list[str], *, reason: str = "manual",
                       force_full: bool = False) -> ReloadResult: ...

class ReloadResult:
    ok: bool
    targets: list[str]
    affected: list[str]          # 含反向依赖者
    pages_destroyed: int
    pages_built: int
    rollback: str                # none / files / runtime / failed
    code: str                    # 成功为空；失败为稳定错误码
    message: str

窗口层只负责页面与导航：reload_plugin_in_place(plugin_id, reason)。 runtime 不 import Qt，继续保持现有的分层边界。

二阶段可做
  • 开发目录文件监听：sllkgui run --plugin-dir ... --watch，防抖后只重载目标开发插件。
  • 不写 registry、不改变版本；失败只隔离开发插件，不影响已安装插件。
  • 左菜单增量 remove/add，减少大量插件时的闪烁。
  • 可选 Surface 状态协议：on_surface_save_state() / on_surface_restore_state()，用鸭子类型探测，不强制。
  • 设置窗口在重载期间的草稿冲突提示。
  • 重载历史与诊断面板（最近 N 次耗时、回滚、错误码）。
触发条件
  • MVP 的选择性重载已稳定，且无重复菜单/托盘/快捷键回归。
  • 开发插件数量或迭代频率足以证明 watcher 的收益。
  • 出现“页面状态必须无损”的真实插件诉求，再设计状态协议。
  • 插件数达到 50+，菜单重建出现可感知闪烁。
明确不做的能力
能力原因替代方案
原生扩展热替换进程内无法卸载已加载的 .pyd/.so/.dll；Windows 文件锁定检测后要求重启；或不支持该类插件热更新
插件线程/定时器强制回收无可靠的全进程 QObject 枚举与强制终止手段插件规范 + 重复重载测试 + 失败隔离
进程隔离 / 沙箱EXT-01 中期规划；与热重载不是同一问题独立立项；IPC/服务发现另行设计
多版本 API 共存SUPPORTED_API={2}；旧版清单直接拒绝插件升级清单 api；基座不做兼容探测
插件数据自动回滚数据 schema 属于插件；基座不知道迁移语义插件自建备份/版本；基座只保留目录
基座/主题/guicore 热替换不在插件生命周期内；会破坏 Qt 对象与全局状态重启应用或开发期重跑

验收标准

验收的核心不是“功能能跑”，而是“未受影响的插件和页面确实没被动过”，以及失败时能回到已知可用状态。

功能验收

功能验收用例
ID场景通过判据测试类型
HR-01两个插件 A/B，重载 AB 的 on_load/on_unload 计数不变；B 页面对象身份不变单元/集成
HR-02A 更新后重载A 的 helper 模块读到新值；旧 sys.modules 条目不存在单元
HR-03停用 AA 的 Surface 路由、菜单按钮、托盘动作、快捷键、事件订阅、服务、设置页全部移除集成
HR-04启用 A只加载 A；其它插件计数不变；A 的菜单/托盘/快捷键恢复集成
HR-05当前页面是 B，重载 AB 页面实例不变；无页面过场；当前路由不变窗口测试
HR-06当前页面是 A，停用 AA 页面被移除；导航回退到默认/原生页；无空白页窗口测试
HR-07A 提供 service，B 依赖 A；更新 AB 也被重载；B 解析到新 service；无旧对象残留集成
HR-08更新失败（新版本 import/on_load 抛错）旧版本恢复；registry 版本回退；错误码可见；旧页面可用故障注入
HR-09更新后菜单标题/插件语言变化无需切换语言即可看到新标题/新文案集成
HR-10更新前后日志版本号新日志前缀为 @新版本，不残留旧版本单元
HR-11原生扩展插件返回 RESTART_REQUIRED；不尝试替换文件；旧版本继续可用单元
HR-12重载进行中再次请求返回 PLUGIN_RELOAD_IN_PROGRESS；无并发卸载/加载；状态不撕裂并发测试

非功能验收

性能与资源
  • N ≥ 20 时，单插件重载 ≤ 全量 30%；轻量插件无页面重建时 ≤ 50ms。
  • 未受影响页面构建数为 0；插件管理页构建数为 0。
  • 连续 20 次启停后，菜单/托盘/快捷键/事件订阅无重复，数量回到基线。
  • 旧页面对象在事件循环后销毁；无持续增长的 QWidget 数量。
  • 重载事件包含 duration_ms / pages_destroyed / pages_built / rollback。
兼容与稳定性
  • API v2 插件无需修改即可被选择性重载。
  • 全量重载回退可用；safe mode 行为不变。
  • 依赖者/提供者顺序正确；服务解析不再拿到旧实例。
  • 设置窗口在重载期间保持可用；插件页刷新且草稿不丢。
  • 架构守卫仍通过：guis 不 import gallery；gallery→guis 仅限组合根。

人工验收

  • 插件管理页：启用/停用/更新/回滚/卸载后仍停留在本页，模式、搜索词、选中项、滚动位置不变。
  • 打开插件 B 页面，更新插件 A：B 页面不闪、不重建、表单内容与滚动位置不变。
  • 打开插件 A 页面，更新 A：页面重建，但 A 通过 settings/storage 恢复草稿；on_surface_leave/enter 各一次。
  • 托盘菜单与快捷键在启停后即时反映；停用插件不再出现在托盘，重新启用后恢复。
  • 设置窗口打开时更新插件：对应插件页刷新，未保存草稿保留，其它页不受影响。
  • 制造坏版本：旧版本恢复运行；错误提示含插件 ID、错误码与日志入口；registry.json 与 UI 一致。
